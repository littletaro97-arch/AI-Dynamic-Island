# 系统通知分批显示与具体标题屏蔽

## 基线与现场证据

开始排查时运行的是安装版 v0.7.4，ProductVersion 为 `0.7.4+2460c757aad779d398a0b14eda4587a89a842e8b`，使用既有安装目录。这是最新公开发行，但未包含本地 `1b0eaf3` 的 Codex 重置预告修复。本轮在该本地源码基础上创建 `codex/notification-batches-and-filters`，不更新发行版本号或 GitHub。

旧逻辑收到一条通知即展示一条，其余最多保留 20 条。配置六行也没有组合多条消息；连续到达会反复启动下一条显示计时。

只读现场采样确认：来源应用身份 `com.oplus.devicespace`，显示来源 `OPPO 互联`，标题 `手机 VPN 常驻通知`。数秒内观察到通知编号 连续变化的编号，创建时间和正文摘要同时变化。因此这是持续生成的新通知，不能靠“相同编号去重”解决。本次不记录其他通知正文，不恢复此前暂缓的微信通知接收调查。

## 实现

- 按用户选择依次显示全部：六行每批三条，四/五行每批两条，二/三行每批一条；一行退化为单条紧凑显示。每条第一行为来源与标题，第二行为正文，超宽文本省略。
- 同一次监听快照只安排一个 Dispatcher 后台展示回调，先完整入队，再组装批次。后续快照进入下一批，保证每批获得独立显示时长，不因为新消息到达重置当前批次的计时。
- 每行独立绑定来源身份，点击打开自己的应用。每行的 × 按“来源身份＋具体标题”屏蔽；设置 → 提醒 → 已屏蔽通知提供逐条恢复入口。规则保存在 settings.json，应用方案不会清掉当前屏蔽规则，也不会把个人通知标题保存到视觉方案中。
- 本机采用用户确认的 FLCLASH 标题规则；不按 OPPO、VPN 或正文关键字整体过滤，所以其他手机消息保留。屏蔽不删除 Windows 通知中心的消息。恢复后等待新的通知更新，历史通知仍不重放。
- 待回答提醒暂停并保存整批通知，恢复时排在新消息之前。主动点击底部横条结束本轮活动和待显示通知，避免旧队列再次展开；之后新到达的消息正常提醒。
- 等待队列最多 512 条，异常洪水超限时提示去通知中心查看；正常批次按到达顺序全部展示。同一编号的待显示内容更新替换旧内容；同一编号只有时间修正不产生新提醒。不同编号的相同正文仍是独立消息。

## 开销与验证边界

复用原显示定时器和监听周期，不增加常驻定时器。活动视图最多三行组；状态重复刷新复用原控件，内容变化才重建和渐显。规则匹配在内存进行，屏蔽/恢复才后台写设置快照，保存序号防止旧异步快照覆盖后续配置。

Release 构建无警告/错误。DisplayNotificationChecks 238 项（含离屏六行真实布局、批次顺序、五行容量、独立点击身份、消息等待独立时长、待回答暂停、主动收起、标题过滤、时间修正、重置预告回归），SettingsChecks 58 项、PerformanceChecks 49 项通过。离屏截图检查了三组通知及设置恢复入口。测试未发送聊天消息、未调用实际通知来源应用，也不代替真实手机通知和桌面视觉验收；这些检查不证明 CPU 占用降低。

验收重点：六行同时接收八条消息应依次显示 3/3/2 条；五行应显示 2/2/2/2 条；持续 VPN 通知不展开岛，其他 OPPO 消息仍显示；恢复该规则后新 VPN 通知可再次上岛；底部横条结束当前积压，后续新消息仍能正常提醒。

Windows 接口边界参考：[通知监听 API](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/notification-listener)。当前接入按 Windows Toast 的来源、标题、正文、编号和时间判断，没有据此声称可靠识别所有 Android 常驻通知类型。
